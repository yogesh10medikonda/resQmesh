ResQMesh Live Demo Script

ResQMesh lets volunteer phones pass emergency SOS messages to each other over Bluetooth when there's no internet or cell signal — proven working, phone to phone, with zero infrastructure.

Total time: ~5-6 minutes. Requires two Android phones with ResQMesh installed and paired via Bluetooth beforehand. Practice this once before presenting live — the timing matters more than the words.

Before You Start (do this 5 minutes before the demo, not during)
 Both phones fully charged
 ResQMesh installed on both
 Phones already paired with each other via Android Bluetooth settings
 Both phones: Wi-Fi OFF, mobile data OFF, Bluetooth ON, Location ON
 Clear out old test messages if possible (or just be ready to say "these are from earlier testing")
 Phone screens set to stay awake / not auto-lock during the demo
1. The Hook (30 seconds)

Say:

"During a disaster — a flood, an earthquake — the first thing that goes down is the phone network. No signal, no internet. So how does someone send an SOS, or how do volunteers coordinate? That's the problem ResQMesh solves."

Do: Hold up both phones, visibly show Wi-Fi and mobile data are OFF on both (open quick settings panel briefly).

Say:

"Both these phones right now have zero internet connection. No Wi-Fi, no mobile data. Everything you're about to see happens entirely offline."

2. Create an SOS Message (45 seconds)

Do: On Phone B, open ResQMesh → tap Send SOS.

Say:

"Let's say someone's trapped near a bridge after a flood. A volunteer fills out a quick SOS — type of emergency, message, and location."

Do: Select "Flood" as the type, type a short message like "Family trapped, water rising, need boat," location "Near Ganga bridge, east side." Tap Save SOS Message.

Say:

"That's saved locally on this phone's own database — completely offline. Right now, only this phone knows about it."

3. Show It's Just Sitting There, Isolated (20 seconds)

Do: Navigate to My SOS Messages on Phone B, show the message with status "stored."

Say:

"Status: stored. Meaning it exists, but it hasn't gone anywhere yet. This is where most offline apps would just stop — the message is trapped on one phone. This is where ResQMesh's actual innovation kicks in."

4. The Bluetooth Relay (90 seconds — the main event)

Do: On Phone A, open ResQMesh → Send / Receive via Bluetooth → tap Start Listening for Messages.

Say:

"This phone represents another volunteer, maybe one who's closer to a rescue point. It's now listening for any nearby ResQMesh phone that wants to pass along a message."

Do: On Phone B, open Send / Receive via Bluetooth, show Phone A's name in the paired devices list, tap Send All Stored next to it.

Say:

"Phone B now forwards every SOS message it's holding to Phone A — over a direct Bluetooth connection. No towers, no internet, no infrastructure at all."

Do: Let both screens update — Phone A should show "Connected. Receiving data..." then "Done. Received 1 message(s) total."

Say:

"And there it is — message transferred, phone to phone, entirely offline."

5. Prove It Actually Worked (30 seconds)

Do: On Phone A, go to My SOS Messages — show the message that just arrived, tagged "(received via Bluetooth)."

Say:

"This message physically moved from one phone's database to the other's. It's not a simulation — it's a real transfer."

Do: On Phone B, go to My SOS Messages, show the same message's status is now "forwarded" instead of "stored."

Say:

"And Phone B knows it successfully passed it along, so it won't waste time re-sending it."

6. The Bigger Picture (30 seconds)

Say:

"In a real disaster, this same handoff happens across many volunteers — Phone A hands to Phone B, B hands to C, and so on, until someone reaches a working network or a rescue point. That's called store-and-forward, and it's the same basic principle used in real delay-tolerant networking systems for exactly this kind of scenario."

7. What's Next (20 seconds)

Say:

"Right now this works phone-to-phone. The next phase is: once any volunteer's phone regains internet, it automatically syncs everything it's carrying to a central server, so rescue teams see it immediately — no one has to physically deliver the message. After that, we're planning offline maps, volunteer verification, and multilingual support."

If Something Goes Wrong Mid-Demo
Bluetooth transfer fails on first try: Don't panic — say "Let's give it another shot, this auto-retries up to three times" and let it retry. This is a real, expected part of the system, not a bug to hide.
A device isn't showing in the paired list: Say "Let me double check they're still paired" and re-check Bluetooth settings briefly, or skip to showing the "My SOS Messages" screen from an earlier successful test instead.
Total Bluetooth failure: Have a screenshot or short screen-recording of a successful transfer ready as backup, and say "Here's a transfer we captured earlier" — judges/professors respect honesty about live-demo risk far more than a stalled silence.
One-Line Summary (if asked to describe it in a sentence)

"ResQMesh lets volunteer phones pass emergency SOS messages to each other over Bluetooth when there's no internet or cell signal — proven working, phone to phone, with zero infrastructure."
